# Wiki Integrity and Canonical Graph Design

**Status:** Approved design — implementation not started  
**Date:** 2026-08-06

## Purpose

Make the Memex long-term wiki reliable as it grows: retain useful, source-backed knowledge; prevent low-value, duplicated, unsupported, or misclassified material from becoming canonical; and keep the default Obsidian graph limited to active semantic knowledge.

The design preserves Memex's existing three memory layers:

```text
raw/        immutable episodic evidence
workspace/  automatic, disposable working memory
wiki/       durable, canonical semantic knowledge
```

It adds controlled internal operational state under `.memex/` rather than adding a fourth visible knowledge layer.

## Goals

1. Make `wiki/` contain only current, canonical, retrievable knowledge.
2. Require evidence and a promotion policy before LLM-derived knowledge reaches `wiki/`.
3. Automate only low-risk, high-confidence operations; route ambiguous or high-impact changes for review.
4. Repair the existing wiki in small, reversible, evidence-backed lots.
5. Keep derived indexes, reports, proposals, and history out of the canonical graph and normal recall.
6. Preserve every raw source and every applied mutation for audit and rollback.
7. Replace decorative wikilinks with sparse, justified semantic relationships.

## Non-goals

- Do not replace `raw/`, `workspace/`, or the Markdown/Obsidian model.
- Do not require manual approval for all useful knowledge.
- Do not silently delete content or source material.
- Do not turn generated reports or project views into canonical facts.
- Do not re-synthesize the entire existing wiki in one destructive batch.

## Current problems addressed

The current synth path can fall back to a technical `note-<id>` slug when proposal identity is missing. It writes directly to the canonical wiki, then relies on post-write gardening suggestions to find near-duplicates. The current linking policy also requires two to six related pages and permits loose thematic associations, which can turn the graph into a dense but weakly meaningful mesh.

Generated artifacts are currently mixed into visible wiki paths:

- `wiki/_sugestoes.md` is a gardening report.
- `wiki/projects/_index.md` and `wiki/projects/<project>.md` are regenerated project views.
- root `index.md` is a generated catalog.

These are generated by the code, not LLM hallucinations, but they are not canonical knowledge and should not appear as graph nodes or factual recall candidates.

## Canonical storage contract

```text
raw/
  immutable source transcripts and adopted source material

workspace/
  current per-workspace handoff pages; automatic and replaceable

wiki/
  topics/
  entities/
  decisions/
  only current canonical pages

.memex/
  review/
    pending/
    applying/
    applied/
    rejected/
    stale/
  audit/
    latest.md
    latest.json
    merge-suggestions.md
  views/
    brain-index.md
    projects-index.md
    projects/
  history/
    wiki/
    manifests/
```

### Graph contract

The default graph contains only `wiki/topics/`, `wiki/entities/`, and `wiki/decisions/` pages with `status: current`.

It excludes all paths in `.memex/`, all raw evidence, working memory, generated views, audit reports, proposals, and archived/superseded pages. Normal recall and embeddings use the same canonical set.

A wikilink is valid only when its target is an existing current canonical page and the relationship is useful and supported by the source material. Zero links are valid for an independent page. There is no minimum link count and no lexical-overlap-only link fallback.

## ChangeSet: the unit of mutation

The LLM no longer writes directly to `wiki/`. It creates a structured `ChangeSet` under `.memex/review/`.

A ChangeSet represents exactly one operation:

```text
create | update | merge | reclassify | archive | repair
```

Minimum fields:

```json
{
  "id": "stable-change-id",
  "state": "pending",
  "operation": "update",
  "created_at": "2026-08-06T00:00:00Z",
  "source": {
    "raw": "raw/source.md",
    "raw_sha256": "..."
  },
  "target": {
    "slug": "existing-page",
    "expected_page_sha256": "..."
  },
  "classification": {
    "section": "topics",
    "slug": "semantic-kebab-case",
    "title": "Human Semantic Title",
    "project": null
  },
  "claims": [
    {
      "text": "A narrow, durable statement.",
      "type": "process",
      "explicitness": "explicit",
      "evidence": [
        {
          "raw": "raw/source.md",
          "raw_sha256": "...",
          "start_line": 42,
          "end_line": 46,
          "quote_sha256": "..."
        }
      ]
    }
  ],
  "proposed_diff": "unified diff or structured page mutation",
  "verification": {},
  "risk": "low",
  "reason": "Why this operation is proposed"
}
```

The `expected_page_sha256` protects against applying an old proposal over a newer canonical page. A mismatch makes the ChangeSet `stale`, requiring regeneration and revalidation.

## Evidence-first promotion pipeline

```text
raw evidence
  → proposer creates ChangeSet
  → deterministic structural checks
  → claim-evidence verification
  → independent fidelity verification
  → risk policy
      → automatic apply
      → pending review
      → archive
      → reject
```

### 1. Deterministic integrity gate

No LLM judgment is needed to reject a malformed proposal. The gate verifies:

- source file and source hash exist;
- line anchors exist and quote hashes match;
- title, slug, section, and operation are valid;
- slug/title are semantic and do not contain a fallback identifier, path, URL, or prompt fragment;
- target page exists for operations that require one;
- no operation writes to `.memex/review`, `.memex/audit`, `.memex/views`, or `.memex/history` as canonical knowledge;
- all outgoing wikilinks target existing current canonical pages.

Failure rejects the proposal without writing to `wiki/`.

### 2. Claim-evidence gate

Every new durable claim needs one or more evidence anchors. The local verifier checks that each quote exists in the declared raw source. A separate verifier classifies each claim:

```text
supported | partial | unsupported | conflicting
```

Only `supported` claims are eligible for automatic publication. `partial`, `unsupported`, and `conflicting` claims never enter automatic promotion.

### 3. Independent fidelity gate

The writing/proposal call and verification call are distinct. The verifier receives the source anchors, claims, current target page, and proposed diff; it checks whether the diff adds unsupported material, loses material, or changes scope.

The verifier may share a provider with the proposer, but it must be a fresh completion and cannot trust the proposer's self-reported confidence. A verifier failure, timeout, or ambiguous result fails closed into review rather than publishing.

### 4. Risk policy

#### Automatic apply: only qualified low-risk changes

- deterministic repair of metadata, links, or derived views;
- update to an existing topic with explicit, supported, low-impact claims;
- creation of a new topic only when identity is semantic, evidence is explicit, no duplicate/stronger target exists, and all verification gates pass;
- mechanical duplicate merge where equivalence and destination are unambiguous.

#### Review required

- all new entities and decisions;
- changes involving a person, team, ownership, commitment, deadline, preference, or sensitive/high-impact fact;
- semantic reclassification;
- ambiguous merge or competing canonical targets;
- conflict between sources or current pages;
- uncertain title, scope, or evidence.

#### Archive or reject

- current content demonstrably unsupported by available declared sources is archived automatically;
- structurally corrupt, invented, or unsafe content is rejected or archived according to whether a prior canonical page exists;
- neither outcome deletes raw evidence.

## Review experience

The primary interface is conversation plus CLI. The MCP exposes structured review operations so an agent can explain evidence, proposed diff, risk, and recommendation without editing canonical pages directly.

```bash
memex audit --dry-run
memex audit
memex review
memex review show <id>
memex review approve <id>
memex review reject <id> --reason "..."
memex review edit <id>
memex review rollback <id>
memex health
```

Conversation equivalents include:

```text
Tem pendências no meu brain?
Mostra as propostas de alto impacto.
Por que esta página foi arquivada?
Aprova as três correções mecânicas.
Reverte a consolidação X.
```

Approval re-runs all gates. If a source or target hash has changed, the ChangeSet becomes `stale`; it is never applied based only on the old approval.

## Mutation and rollback

Only a promoter component may mutate `wiki/`. It applies a ChangeSet serially:

1. Revalidate source and target hashes.
2. Validate canonical paths and outgoing links.
3. Apply the page mutation.
4. Rewrite incoming links for a merge or rename.
5. Move absorbed/archived material and its manifest to `.memex/history/`.
6. Rebuild canonical index and generated views.
7. Refresh embeddings only for canonical current pages.
8. Append a transaction record, changelog event, before/after hashes, changed paths, and link map.

For a merge, the selected destination remains current. The origin is moved to history with `status: superseded`, `superseded_by`, source preservation, and a manifest. All incoming `[[origin]]` links are rewritten before the origin leaves the visible wiki.

For archive, the original page is moved intact to history with `status: archived`, a reason, source-verification outcome, and a manifest. It is removed from canonical index, normal recall, embeddings, and graph.

`memex review rollback <id>` restores all paths, index entries, link rewrites, and prior page text recorded in the transaction.

## Existing-wiki recovery

Recovery is an audit-led migration. It begins read-only and works in small lots.

```text
wiki + index + raw + adopted documents
  → memex audit --dry-run
  → anomaly report + ChangeSets
  → automatic application only for qualified mechanical repairs
  → review inbox for semantic changes
  → before/after health report
```

The auditor classifies every canonical page:

| Classification | Action |
|---|---|
| Healthy | Keep current |
| Mechanical repair | Apply automatically |
| Unambiguous duplicate | Merge automatically and retain history |
| Semantic ambiguity | Create review ChangeSet |
| Unsupported | Archive to history |
| Conflict | Send to review; never resolve automatically |

Evidence lookup order is: declared page sources, referenced raw notes, adopted documents, page changelog/history, then related current pages only for conflict detection. A lack of a perfect anchor is not proof of falsehood; it prevents a page from staying current under the selected policy and results in a reversible archive decision.

### Recovery lots

```text
Lot 0: migrate generated artifacts to .memex/audit and .memex/views.
Lot 1: repair technical identities: note-<id>, path-like, URL-like, and prompt-like titles/slugs.
Lot 2: merge only strong mechanical duplicates.
Lot 3: assess evidence and semantic classification.
Lot 4: repair graph quality: dead links, stale links, and decorative links.
```

Each lot emits a report with counts, reasons, affected ChangeSets, and before/after health metrics. No bulk rewrite occurs without reviewing the dry-run output for that lot.

## Generated views and artifacts

Generated content is explicitly noncanonical:

```text
wiki/_sugestoes.md         → .memex/audit/merge-suggestions.md
wiki/projects/_index.md    → .memex/views/projects-index.md
wiki/projects/<project>.md → .memex/views/projects/<project>.md
index.md                   → .memex/views/brain-index.md
```

Views are rebuilt deterministically from the canonical index. They do not have embeddings, do not appear in regular recall, do not count as canonical pages, and do not appear in the default graph.

## Health reporting

`memex health` and `.memex/audit/latest.{md,json}` report:

- current page counts by section;
- review queue count and age;
- publication, review, rejection, archive, and rollback rates;
- current pages with verified evidence;
- invalid slugs/titles;
- confirmed and candidate duplicates;
- dead, invalid, rewritten, and low-value links;
- current conflicts;
- distribution of page sections and lifecycle outcomes;
- a sampled fidelity measure from canonical page claims to sources.

`memex status` exposes the short actionable summary, for example:

```text
wiki: 642 current · 7 in review · 0 invalid slugs
health: 98% with verified evidence · 2 conflicts require review
```

## Failure behavior

The system fails closed:

| Failure | Result |
|---|---|
| Proposer unavailable | Raw remains pending; no wiki mutation |
| Verifier unavailable/ambiguous | Proposal becomes pending review |
| Source or target hash mismatch | Proposal becomes stale |
| Index inconsistent | Rebuild canonical index before mutation |
| Interrupted transaction | Recovery restores or completes from transaction manifest |
| Removed/archive link target | Remove or rewrite before publish; never leave dead canonical link |
| Current source conflict | Review only |

## Test strategy

### Deterministic tests

- fallback/technical slug never becomes current;
- nonexistent evidence anchor rejects the ChangeSet;
- raw or target hash change makes proposal stale;
- review/audit/view/history paths never enter canonical index, recall, embeddings, or graph;
- every current page has a semantic identity and valid evidence source;
- every canonical wikilink targets an existing current page;
- merge rewrites backlinks and preserves origin/history manifest;
- archive removes graph/recall/index visibility and supports restoration;
- generated views are reproducible;
- recovery after interruption leaves no partially applied transaction.

### LLM-mocked tests

Fixtures cover supported, partial, unsupported, and conflicting claims; decisions disguised as topics; inferred ownership; mechanical and semantic duplicates; technical proposal identities; invalid JSON; and unavailable/ambiguous verifiers. All uncertain cases must route to review, reject, or archive rather than automatic publication.

### Real-vault migration tests

Before touching an existing vault:

1. Save snapshot and baseline manifest.
2. Run `memex audit --dry-run`.
3. Inspect report and ChangeSets.
4. Apply only a small approved lot.
5. Verify invariants and before/after report.
6. Exercise at least one rollback.

## Success criteria

After migration and rollout:

```text
0 current fallback/technical slugs or titles
0 operational artifacts in the canonical graph
0 canonical links to nonexistent or noncurrent nodes
100% of current pages have a verifiable source record
all automatic mutations have ChangeSets and rollback data
no automatic publishing of decisions, people, commitments, preferences, or conflicts
new duplicate candidates are stopped before canonical publication
```

## Research basis

The design follows the recurring conclusions in recent work on durable agent memory:

- Memory extraction and updating can introduce persistent hallucinations, so they must be evaluated separately from answer quality: [HaluMem](https://arxiv.org/abs/2511.03506).
- A memory transition should be verified for coverage, preservation, and faithfulness: [TrustMem](https://arxiv.org/abs/2606.25161).
- Long-term memory needs provenance, clear read/write separation, and stronger auditing for reflection/consolidation paths: [A Survey on the Security of Long-Term Memory in LLM Agents](https://arxiv.org/html/2604.16548v1).
- Typed separation between evidence, retrieval cues, and truth-bearing claims prevents unsupported text from becoming factual memory: [MemIR](https://arxiv.org/abs/2605.25869).
- Long-lived systems benefit from layered provenance-preserving storage plus a curated retrieval view: [Ground Truth First](https://arxiv.org/html/2607.21962v1).
